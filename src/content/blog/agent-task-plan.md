「让模型直接调用工具」是搭建 Agent 最顺手的起点，也是最容易失控的起点。

模型拿到一句「查询洪山区的行政区边界」，输出一串工具调用，后端照单执行。原型阶段这确实很快。但随着工具数量涨到十几个、任务复杂度涨到多步，你很快会遇到几个具体问题：

- 同样的问题两次得到不同的执行路径，没法复现；
- 模型调错了参数，错误发生在哪一层说不清楚；
- 想给某个工具加约束，得去改提示词，改完还担心影响别的任务；
- 模型偶尔会「自己发明」一个不存在的工具或参数名。

这些问题的共同点是：把模型的自由度直接暴露到了系统边界上。

## 把中间加一层：TaskPlan

我的做法是让模型只负责产出**意图**，不负责执行。中间插入一个结构化的任务计划：

```text
用户请求
  -> DomainSelector      # 先确定这次该用哪个领域的能力目录
  -> Planner             # 规则引擎或模型，产出计划
  -> TaskPlan            # 结构化数据，schema 校验
  -> ToolRegistry        # 按契约分发，模型不直接调用后端
  -> SpatialToolAdapter  # 适配真实 GIS 或内存演示后端
```

关键在于 `TaskPlan` 是**数据**，不是代码。它有一份 schema，可以被校验、版本化、存进数据库、回放。计划里的每一步都声明了要调用哪个工具、传什么参数、以及依赖哪些前序步骤。

这一步带来的直接好处是：模型的错误从「执行时炸了」变成了「计划生成时就过不了 schema」。参数名拼错、缺必填字段、依赖了不存在的步骤，都会在进入执行层之前被拦下。

## 工具契约：模型表达意图，Registry 决定怎么执行

工具契约是这个设计里我最看重的一环。

模型产出的是「我想调用边界查询工具，参数是某某区」这样的**意图描述**。真正把意图变成一次后端调用的是 `ToolRegistry`：它拿着契约检查工具是否存在、参数是否合法、当前运行时是否允许这个领域的工具被执行，然后才派发。

```python
# 伪代码：模型能表达的东西，到这一层会被重新裁定
intent = plan.steps[i].intent
tool = registry.resolve(intent.tool, domain=current_domain)
tool.validate(intent.params)      # schema 校验，失败即中止
result = adapter.dispatch(tool, intent.params)
```

好处有三层：

1. **后端永远不会被模型直接触碰。** 模型表达「想做什么」，Registry 决定「允许做什么」。
2. **约束可以写在代码里，而不是提示词里。** 要禁止某个领域访问写操作，改 Registry 就行，不存在模型「忘了遵守」的问题。
3. **每个领域可以跑在独立的运行时里。** GIS 后端和文本后端互不干扰，一个崩了不会污染另一个。

## Planner 也应该可替换

如果 Planner 只有模型实现，那么离线跑测试、复现 bug 都会变得很难。

在 Spatial Agent 里我把 Planner 做成了可替换的接口，至少提供两种实现：

- `rule` —— 规则引擎，离线、确定性，输出固定。测试和演示用它。
- 模型实现 —— 通过 sidecar 调用，处理规则覆盖不到的开放式表达。

这套东西在 CI 里跑得飞快，因为测试根本不需要网络、不需要 API key、也不需要任何随机性。模型的输出质量问题，可以单独用「模型实现 vs 规则实现」的差分测试去覆盖。

## 剩下的问题

把执行路径固定下来之后，真正难的部分浮出来了：结果对不对。

一个任务计划通过了 schema 校验，执行也成功了，但「坡度 > 15% 且土地利用类型是林地」这个筛选结果到底可不可信？这不是执行层能回答的问题 —— 它取决于数据的 CRS、覆盖范围、栅格是否对齐、几何有没有问题。

所以我在计划层之上又加了一层**证据**：每次工具调用都记录输入、参数、schema 版本和结果来源，让最终结论能被一路追问回去。

这部分我另外写了一篇，见[让 Agent 的 GIS 结论可被追问](https://serate.github.io/blog/evidence-chain/)。

## 一点体会

「模型负责意图，系统负责执行」这句话听起来很显然，但真正落到代码里的时候，最容易犯的错还是图省事让模型直接调。中间那层结构化数据一开始看着多余，直到你第三次在半夜排查「为什么这次结果和上次不一样」的时候。

多写的那点 schema，换来的是每次出错都知道该往哪看。
